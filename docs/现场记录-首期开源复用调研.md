# 现场记录首期与开源选型

2026-11-18。首期输入为模拟截图和笔记，目标是验证候选事项、人工分诊、只读分析和人工批准实施的边界。为了保持项目原有的事件权限和版本语义，沿用 FastAPI、Pydantic、SQLAlchemy、React 以及已有 Codex Worker。首期没有新增第三方依赖或外部服务。

## 选型

| 候选 | 上游持续维护的依据 | 可复用之处与本项目取舍 |
| --- | --- | --- |
| PaddleOCR | 发布页展示 3.4、3.5、3.6、3.7 等连续版本，代码仓库使用 Apache-2.0 | 优先验证本地中文截图 OCR。普通 OCR 可以给出文字、位置和识别分数，适合回到图上核对。模型文件、推理引擎、启动耗时要单独测。文字识别之后仍由模型或规则归纳事项。 [发布](https://github.com/PaddlePaddle/PaddleOCR/releases) · [OCR 接口](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html) |
| Tesseract | 上游仍维护发布记录，官方单列不同版本的语言数据 | 作为 CPU 本地基准，用相同中文及中英混排截图实测。可用于文字区块清晰的截图。医院系统中的小字号、表格、弹层和截图缩放需要实测，不能根据文档推断准确率。 [发布](https://github.com/tesseract-ocr/tesseract/releases) · [语言数据](https://tesseract-ocr.github.io/tessdoc/Data-Files-in-different-versions.html) |
| Docling | IBM 发起，公开仓库和持续发布记录，代码使用 MIT | 后续纳入 PDF、表格、复杂报告版面时再评估。它提供本地转换、布局恢复以及 OCR 后端，与字段和版面结构需求匹配。截图首期直接为现有 Worker 提供图片，额外文档解析引擎的收益有限。 [能力](https://docling-project.github.io/docling/) · [发布](https://github.com/docling-project/docling/releases) |
| Label Studio | 上游发布页含稳定版 1.23.2，并有持续构建记录 | 可做离线标注与质量抽检，保存人工对事项类型、拆分边界和证据关联的标准答案。社区版适合实验；官方对比表将角色化审批和细粒度权限列为商业功能。项目上已有事件所有权和审核语义，业务审核继续使用内置流程。 [发布](https://github.com/HumanSignal/label-studio/releases) · [版本能力](https://labelstud.io/guide/label_studio_compare) |
| Temporal | 服务端持续发布，官方文档解释持久历史与恢复 | 当转写、截图提取、重试和人工等待构成长时间跨进程流程时再评估。引入后要运行独立服务、维护 Worker 和升级历史执行语义。首期候选审核与入站能在当前数据库一笔事务完成。 [发布](https://github.com/temporalio/temporal/releases) · [工作流机制](https://docs.temporal.io/workflows) |
| FFmpeg + whisper.cpp | 两者维护独立发布渠道，whisper.cpp 提供本地 CPU 推理和 Windows 构建说明 | 第二阶段分别负责媒体提取和本地转写。用医院缩写、多人交谈和噪声样本比较结果。二进制和模型单独锁版，FFmpeg 的再分发取决于所用构建组件，打包前确认实际构建。 [FFmpeg 发布](https://ffmpeg.org/download.html) · [许可证说明](https://www.ffmpeg.org/legal.html) · [whisper.cpp 发布](https://github.com/ggml-org/whisper.cpp/releases) |

下一轮比较 OCR 时，固定一份脱敏评测集，覆盖中英混排、长字段、暗色主题、表格、小字和无文字误差的布局问题。记录 Windows CPU 冷启动与单图耗时、关键字段正确率、无证据条目比率、人工修改量和可完全离线运行的条件。截图上的文字坐标与识别分数只作为原图定位信息。项目身份、批准与否和任务类型来自后台权限及审核记录。

## 参考交互

- GOV.UK 的 Check answers 把核对放在提交之前，并保留修改路径。现场候选逐条显示原文、可编辑字段和明确的提交动作。 [Check answers](https://design-system.service.gov.uk/patterns/check-answers/)
- GitHub Issues 让用户确认项目与问题标题，再创建问题。本项目同时提供已有只读事件列表，便于追加同一问题的新证据。 [Creating an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)
- Label Studio 支持图片与文本共同标注，适合参考并列展示材料与核对结果。证据沿用工作台原有样式，不引入标注平台。 [Labeling guide](https://labelstud.io/guide/labeling)

## 首期落地

- 管理员在「现场记录」选项目并提交资料。离线整理器按非空笔记行生成候选，识别 `Bug：`、`需求：` 和 `[截图1]` 等标记。没有引入真实模型识图；未关联的截图单独生成待澄清事项。
- 确认后将候选、标准事件和只读任务关联写入同一事务。支持同项目、状态可补充的只读事件。版本变化时拒绝旧关联操作；重复提交返回原结果。
- 现场截图复用受管附件目录和 Worker 校验，经过审核才加入 Worker 材料。只读结果符合本轮证据要求后，人工填写范围与验收条件，创建独立实施任务。批准记录保留分析任务、版本和证据引用。
- 用隔离数据验收。录音录屏与自动审批留待后续阶段。正式试点前验证真实模型、截图整理质量和现场数据处理范围。

- 第二轮 1440×1000、1024×900、390×844 三项均通过。事件详情的「消息」页可读回截图，页面无横向溢出。复查了笔记换行、审核按钮、事件标题和证据链接。截图与轨迹位于 `.test-tmp/design-workflow-visual/2026-11-18T07-29-39-982Z/results/`。
- 模拟 Codex 端到端验证使用临时 Git 仓库。只读 Worker 读取 README，提交第二条现场消息后重新核验。人工批准实施和文件写入后，修复 Worker 在隔离目录生成测试文件，项目验证命令实际退出为 0，原目录未产生文件。
