# SuperAgent 产品设计文档

版本：v0.2 实施设计稿
日期：2026-11-13  
定位：个人与小团队的持续在线研发协作助手  
配套文档：[技术执行文档](./SuperAgent-技术执行文档.md)

SuperAgent 持续接收研发工作中的请求和变化，把它们归入可追踪的任务，在独立工作区中并行执行，并将结果、证据和需要人决定的事项集中呈现。用户可以在工作台、钉钉或 Redmine 补充要求，不需要记住任务由哪个底层会话执行。

本轮主流程为钉钉 @本人或授权群明确请求、Redmine 指派／评论变化 → 已绑定项目目录与基线分支 → Windows/Linux 独立工作区 → Codex 分析、修改与验证 → 展示证据和回复草稿 → 有效授权后回复原渠道 → 人工验收。接入器默认禁用真实账号监听，业务数据恢复先交付方案。

本方案以指定的 [SuperAgent 构思笔记](D:/myfiles/daily/daily/00-Inbox/SuperAgent.md) 为基础。用户已确认首阶段面向个人／小团队研发协作；功能分期、界面、权限规则、指标和排期是本产品的设计决策。文档描述待开发的目标产品，原文的实验数据不作为本产品已经达到的效果。

## 1 产品目标与使用人群

### 1.1 要解决的问题

研发人员同时处理问题排查、代码修改、评审反馈和验证时，必须在多个会话和平台间恢复背景、传递新要求、检查是否卡住。任务执行能力提高后，组织任务和验收结果仍持续占用人的注意力。

第一阶段把这部分组织工作交给系统：接收需求后及时确认，将后续反馈持续关联到同一任务；后台执行期间接受新要求；发生阻塞时带着证据请求介入；完成后提供可审阅的产物。

### 1.2 用户与职责

| 用户 | 主要诉求 | 典型操作 |
| --- | --- | --- |
| 个人开发者 | 同时推进几项工作，减少反复解释 | 发起任务、补充要求、审查改动、接管 |
| 小团队研发负责人 | 掌握交付和阻塞，控制授权和费用 | 设置项目范围、排序任务、批准发布、验收 |
| 团队开发成员 | 在已有研发平台协作 | 钉钉提出请求、Redmine 指派或评论、查看验证结果 |
| 管理员 | 保持系统可靠、控制接入边界 | 配置仓库与模型、绑定身份、管理设备和额度 |

P0 默认服务 1～5 名受信任协作者、一个共享授权项目空间、1～3 个试点仓库和最多 4 个同时执行的任务。这是首轮验收负载，不是产品的硬性规模上限。需要相互保密的项目使用独立实例；跨项目权限隔离和多租户属于后续阶段。

### 1.3 产品原则

1. **用户面对任务。** 工作台展示目标、状态、产物和决定，不要求用户管理 Session。
2. **同一件事持续推进。** 跨入口保留来源和决定；无法确定关联时明确询问，不静默猜测。
3. **执行并行，沟通集中。** 单项长任务不阻塞新请求，重复消息和普通过程不刷屏。
4. **完成必须有证据。** 修改、测试、提交、发布和现场验收分别记录，不能互相替代。
5. **自主程度可配置。** 已有授权持续生效；有副作用的操作受确定性权限控制。
6. **等待是可解释的状态。** 区分缺信息、缺授权、缺设备、主动暂停和真正失败。

## 2 使用场景与端到端体验

### 2.1 场景 A 提出问题并获得可审阅修复

用户在工作台输入：“仓库 A 导出报表时偶尔超时，帮我复现并修复，先给改动草稿。”系统立即返回任务链接和执行范围；资料充分后，在已绑定项目基线建立的独立工作目录中通过 Codex 复现问题、形成修改和验证材料。用户同时提出仓库 B 的评审任务，二者并行推进。

第一项任务完成时，工作台显示问题原因、改动文件、测试范围、失败项和未验证事项，状态为“待验收”。若需要推送分支或创建 PR，展示具体分支、提交内容、接收仓库和消息正文；按项目现有授权直接执行或请求批准。任务的完成条件取决于最初约定：交付改动草稿的任务无需等待上线；要求上线的任务不能以 PR 已创建冒充完成。

### 2.2 场景 B 在钉钉或 Redmine 改变方向

已关联 Redmine 问题或钉钉回复串中，用户评论：“先不要迁移数据库，改成兼容旧字段。”系统核验评论者身份和操作权限，把修改要求加入同一任务，更新目标版本，并停止发起旧方案的后续写入。已产生的文件和测试记录保留为历史版本，未执行的旧批准失效。

新结果明确列出“采用兼容方案”和仍需验证的地方。若评论只是另一个参与者的建议，则展示建议或交给任务负责人决策，不直接覆盖已确认方向。

### 2.3 场景 C 执行环境离线后恢复

任务依赖的执行设备离线时，工作台进入“等待资源”，显示设备名称、最后联系时间和受影响步骤。系统继续接收用户消息、处理其他任务。设备恢复后，先核对已运行命令的结果，再续跑安全步骤；结果未知的发布或推送不能盲目重做。

P0 同时覆盖 Windows 与 Linux 本地 Codex 执行。先绑定固定项目目录、基线分支、允许路径和验证命令，再创建独立工作区，记录 Codex thread/turn 与执行证据。

### 2.4 场景 D 主动发现问题并准备材料

P1 中，管理员可为明确仓库或 IM 群启用“静默分析”。系统对反馈进行判断，只有相关性足够且预算允许才开始只读排查或在隔离目录准备草稿。有可复现问题与可审阅结果时，再提示负责人；低价值结果不通知。

主动工作进入低优先级队列，不抢占明确指令的执行名额；本阶段上限为 1 个主动任务，且占用总并发额度。无明确授权时不发布群消息、推送代码、创建 PR、合并或部署。

## 3 功能范围和版本边界

| 能力 | P0 最小可用版本 | P1 试点增强 | 后续候选 |
| --- | --- | --- | --- |
| 交互入口 | Web 工作台、钉钉 @本人或授权群明确请求、Redmine 指派／评论；GitHub 可选 | 更多事件类型 | 邮件、其他 IM、其他代码平台 |
| 任务组织 | 创建、关联、并发、优先级、干预、验收 | 模板、周期性只读任务 | 项目计划与依赖组合 |
| 路由和记忆 | 规则过滤、Router、订阅直通、带来源的任务摘要和引用召回 | 更细策略、经确认的长期偏好 | 跨实例记忆与 A2A |
| 代码执行 | Windows/Linux 本地 Codex、独立工作目录、测试与产物 | 更多设备能力选择 | 弹性执行集群 |
| 自主行为 | 明确请求驱动；已订阅任务接收 CI 和评审反馈 | 白名单内的静默分析、有限草稿 | 自主处理复杂项目 |
| 人工控制 | 补充／改方向、暂停／恢复、取消、接管、批准／拒绝 | 团队职责和审批策略细分 | 企业级策略治理 |
| 可靠性 | 持久化、幂等、结果对账、规则 Watchdog、人工恢复入口 | 语义停滞检测、受限自动恢复 | 大规模多区容灾 |
| 对外动作 | 发送任务回复、推送任务分支、创建草稿 PR，均受授权约束 | 更多可配置动作 | 自动合并、生产部署需独立立项 |

P0 不包含自主访问任意群聊、任意生产服务器、自动合并或上线、跨组织协作、移动端原生应用、通用桌面控制和无限长期记忆。首版通过 Codex app-server 接入执行能力，模型及推理强度在本机可用能力和项目策略内配置。

“持续在线”的 P0 含义是控制服务可独立运行、事件已接收即持久保存、进程重启可恢复任务。它不意味着设备离线时仍能执行依赖该设备的命令，也不意味着模型服务中断时仍能继续推理。

## 4 核心对象与信息结构

| 对象 | 用户理解 | 必需信息 |
| --- | --- | --- |
| 项目空间 | 一组有共同访问权限的仓库、成员和规则 | 成员、仓库、模型、执行环境、授权和额度 |
| 任务 | 一件有目标、有交付标准的工作 | 目标、负责人、优先级、状态、验收标准、来源、费用 |
| 关联讨论 | 工作台讨论、Issue、PR 或评审串 | 平台、原始链接、参与者、关联任务 |
| 事件 | 请求、评论、CI 结果、执行结果等变化 | 来源、发生时间、接收时间、处理记录 |
| 执行记录 | 某次尝试及其证据 | 输入版本、环境、命令摘要、结果、异常 |
| 产物 | 差异、分析报告、测试结果或 PR | 版本、来源任务、查看入口、验证状态 |
| 决策与授权 | 人明确作出的选择或可复用规则 | 操作者、范围、有效期、关联产物版本 |

一个任务可关联多个讨论，一个讨论也可关联多个任务。收到共享 PR 的新事件时，多个执行者可以收到信息，但对同一分支的写入仍要协调，不能把“都收到了消息”当作避免冲突的保证。

## 5 页面与交互设计

### 5.1 导航和首页

一级导航保持四项：**工作台、任务、项目设置、运行状态**。普通成员默认进入工作台，管理配置由角色控制。

工作台按人的下一步行为安排内容：

```text
项目空间                     新建任务        当前额度
需要你处理  3 项
  补充复现条件   ｜  批准向仓库 A 推送改动   ｜  验收修复结果
正在推进
  报表超时修复   正在验证      最近证据：已复现超时
  接口兼容评审   等待资源      执行环境离线，其他任务正常
最近交付
  导出字段修复   待验收        查看差异、测试及未验证项
```

新建任务只强制要求目标和项目；仓库、完成标准、可执行动作按上下文预填并可修改。没有明确完成标准时，由系统给出一段可编辑建议；无法安全执行的信息缺口放入“需要你补充”。

任务列表支持按状态、仓库、负责人和来源筛选。避免用“运行中”掩盖实际等待；每项任务展示最近一次有证据的进展和下一步。

### 5.2 任务详情

页头固定显示目标、当前状态、负责人和操作入口。主体包含：

| 区域 | 展示内容 | 用户可做的事 |
| --- | --- | --- |
| 当前目标 | 目标版本、执行范围、完成条件 | 补充要求、改变方向 |
| 当前进展 | 最近证据、下一步、阻塞原因 | 补充信息、调整优先级 |
| 产物与验证 | 改动差异、测试结果、报告和原始链接 | 预览、下载、提出返工、验收 |
| 决策时间线 | 关键要求、批准、恢复、失败与完成 | 追溯原因、打开来源 |
| 关联讨论 | 工作台、钉钉、Redmine 的关联关系及可选 GitHub 引用 | 跳转、纠正误关联 |
| 执行详情 | 脱敏后的工具记录、费用、环境 | 展开排查、接管工作目录 |

默认不展示模型内部推理。执行摘要、工具动作和可验证证据足以解释结果；原始日志仅对有权限的用户按需展开。

### 5.3 控制动作的准确含义

| 动作 | 系统行为 | 页面反馈 |
| --- | --- | --- |
| 补充要求 | 记录新信息并加入后续执行上下文 | 已接收；说明是否影响当前计划 |
| 改变方向 | 新建目标版本，使旧方案后续写入和旧批准失效 | 正在调整；显示已发生且无法撤回的动作 |
| 暂停 | 阻止新步骤，允许安全的当前步骤结束或中止 | 暂停处理中，确认后为已暂停 |
| 恢复 | 复核环境、授权和目标后从有效记录继续 | 已恢复或解释新的等待原因 |
| 取消 | 发出停止信号，禁止继续安排动作 | 停止处理中；确认执行结束才显示已取消 |
| 接管 | 暂停自动写入，移交目录、分支、日志和未完成项 | 人工接管中；恢复需重新检查本地变更 |
| 批准／拒绝 | 绑定具体动作和产物版本，继续或重新规划 | 显示批准者、范围和有效期 |
| 验收／返工 | 对照完成条件接受或提出差距 | 已完成或重新进入执行 |

暂停和取消不承诺撤销已经发生的外部副作用。设备离线、命令不可中断或完成回执未知时，继续显示“停止待确认”，同时保留隔离后续动作的保护。

### 5.4 P0 人工接管的实际路径

接管采用“导出修改、人工提交、核对后恢复”的路径。系统先冻结自动写入，待在途命令完成或确认停止后，提供基线提交号、改动补丁、新增文件包、测试记录和未完成清单。执行状态尚未确认时只能导出现有快照，并明确其可能不完整。

用户在自己的工作目录应用这些材料，完成修改后提供允许仓库中的具体提交 SHA；需要远端取回时由用户自行推送已授权人工分支。系统核对仓库归属、基线和人工差异，在新的隔离目录载入该提交。负责人确认恢复后，以新的目标版本继续执行并重新验证。导入冲突、人工提交不属于允许的仓库或在途命令仍未结束时，保持冻结并说明原因。

P0 不要求用户登录服务器或直接编辑运行目录；导出、提交导入和恢复确认构成完整接管流程，不能只提供一个“接管”按钮。

## 6 事件归属与跨入口连续性

### 6.1 归属规则

系统优先使用明确的任务链接、Issue／PR 映射和已订阅讨论。无明确关联时，再结合仓库、参与者、时间和语义判断。多个候选接近时，向用户展示候选任务供选择，不自动合并历史。用户纠正误关联后，原始记录保留，未来事件按新映射处理。

没有独立讨论串的钉钉消息在 P0 中依赖回复关系、任务链接或明确任务选择；不能把整个群的消息归为一个任务。

跨平台身份必须由账号绑定或管理员确认建立。文字姓名相同、评论内容自称负责人、消息里附带账号 ID，均不能作为授权依据。P0 只自动处理已授权成员的明确请求；未授权参与者的内容可以作为待核实资料，但不能成为执行命令。

### 6.2 后续事件处理

首次事件由 Router 判断是否创建或关联任务。归属确定后，后续事件直接进入任务执行邮箱；任务内部处理反馈并汇报关键进展，Router 负责统一对外沟通。取消、暂停、权限撤回和目标变化具有高于普通进度消息的处理优先级。

CI 失败可以驱动原任务继续修复，但只有订阅目标、提交版本和授权范围都匹配才自动推进。无关分支或旧提交的结果归档为历史，不覆盖当前验证结论。任务完成后的新要求保留原验收记录，并新建关联任务；不能静默重新打开已经验收的任务。

## 7 任务状态与通知规则

### 7.1 对用户可见的状态

| 显示状态 | 技术标识 | 进入条件 | 离开方式 |
| --- | --- | --- | --- |
| 排队中 | queued | 已创建，等待执行名额 | 获得执行名额 |
| 执行中 | running | 正在推理或执行工具 | 交付、等待、暂停或失败 |
| 待补充 | waiting_input | 缺少会影响正确性的必要信息 | 用户补充后重排 |
| 待授权 | waiting_approval | 有具体待执行动作，授权不足 | 批准、拒绝后调整或取消 |
| 等待资源 | waiting_resource | 设备、额度、模型或依赖暂不可用 | 恢复并通过检查后重排 |
| 已暂停 | paused | 已停止安排动作且执行状态可确认 | 用户恢复或取消 |
| 待验收 | review_ready | 产物和验证材料齐全 | 验收或返工 |
| 已完成 | completed | 满足约定验收标准并被接受 | 新需求生成关联任务 |
| 失败 | failed | 有限重试用尽或存在无法继续的错误 | 显式重试产生新执行尝试 |
| 已取消 | cancelled | 取消请求已落实且执行终止已确认 | 新需求生成关联任务 |

“正在暂停”“停止处理中”“人工接管中”是状态上的控制提示，需与实际执行状态同时展示。它们不能直接等同于执行已经停止。旧目标产出的迟到结果可留作历史，不得触发当前任务交付。

### 7.2 通知策略

| 事件 | 工作台 | 钉钉／Redmine（GitHub 可选） |
| --- | --- | --- |
| 明确请求已收到 | 即时回执和任务链接 | 原入口一次确认；符合已有消息授权 |
| 普通过程推进 | 更新时间线 | 默认不发送 |
| 需要补充或批准 | 置顶待处理卡片 | 一条简短问题，附具体操作入口 |
| 交付或有实质阻塞 | 产物或阻塞卡片 | 一次结论及详细结果链接 |
| 可自行恢复的短暂错误 | 记录恢复过程 | 不发送 |
| 同一故障持续存在 | 更新原卡片 | 合并；默认最多每 30 分钟一次 |
| 主动分析无可用结果 | 仅授权者可查活动记录 | 保持安静 |

多渠道通知以发起入口为默认主通知渠道；另一个渠道只按需更新关联产物，不重复推送同一状态。钉钉默认限制为约 200 个汉字的摘要，复杂内容放到任务详情。免打扰时段、紧急阻塞例外和收件范围由管理员配置。

## 8 权限、主动性与可控执行

### 8.1 授权等级

| 等级 | 默认动作范围 | 批准方式 |
| --- | --- | --- |
| 观察 | 读取明确授权的仓库、讨论和 CI | 项目接入时授权 |
| 准备 | 通过 Codex 在绑定的独立目录分析、修改和运行允许的验证工具 | 项目策略可长期授权；运行代码仍需环境隔离 |
| 对外交付 | 回复评论、推送任务分支、创建草稿 PR | 预先授予明确范围或逐次批准 |
| 高影响动作 | 合并、部署、删除、扩大权限、访问生产凭据 | 不纳入 P0/P1 自动执行范围 |

接入钉钉、Redmine 或可选 GitHub 时可明确授予“对已绑定任务回复状态”的持续权限，避免每条确认都请求审批。批准具体发布动作时，展示目标、内容、影响范围与验证证据；内容、目标分支或关键权限改变后重新判断授权，不能继续沿用失效批准。

项目已有明确授权时不重复提问。代码、评论、日志和模型输出中的“允许执行”不能扩展权限。系统以可信身份、项目策略和具体动作内容决定能否执行。

P0 使用以下最小操作权限。任务负责人是具体任务上的职责，可以由管理员指定；普通成员创建任务后默认成为该任务负责人。

| 操作 | 管理员 | 该任务负责人 | 其他成员 | 只读成员 |
| --- | --- | --- | --- | --- |
| 查看共享空间任务与脱敏材料 | 可 | 可 | 可 | 可 |
| 创建任务、补充建议 | 可 | 可 | 可 | 不可 |
| 改方向、暂停、取消、接管、恢复 | 可 | 可 | 仅提建议 | 不可 |
| 验收、返工 | 可 | 可 | 仅提建议 | 不可 |
| 批准具体对外动作 | 可，在项目授权上限内 | 仅在管理员授予的批准范围内 | 不可 | 不可 |
| 管理持续授权、成员、设备和额度 | 可 | 不可 | 不可 | 不可 |

管理员也不能通过批准界面执行产品范围外的合并或部署。P0 允许同一人发起并批准自己任务范围内的动作，不承诺双人复核；如团队要求双人复核，应作为接入条件增加相应策略。各渠道绑定账号沿用上述权限，仓库评论权限不会自动获得本系统的任务控制权。

### 8.2 执行环境与隐私

每个任务使用独立工作目录和任务分支，通过系统账号权限、Codex 执行策略与可用隔离机制落实目录、仓库和网络限制。独立 Git 工作区还需完成越界访问负向验证。凭据由受控连接器代为使用，模型不直接获得明文令牌。发给外部模型的数据类别、保留期限和允许的提供商在接入页明确展示。

P0 建议执行日志保留 30 天、任务摘要与审计记录保留 90 天、产物保留 90 天，均可配置并支持清理。被删除内容的引用显示“已清理”，不能让缺失材料被误认为验证通过。备份另按运维保留策略到期清理，前台删除不承诺即时擦除所有备份。

## 9 非功能目标与评估方法

以下是待通过试点验证的目标，不是已测性能或原文实验的复用结果。测试需记录硬件、网络、模型、价格版本、事件负载和样本量。

| 指标 | P0 目标 | 测量方式 |
| --- | --- | --- |
| 请求接收体验 | 持久接收回执 p95 ≤ 2 秒 | 事件进入到持久化确认，不计模型完成时间 |
| 新任务归属 | 正常负载下 p95 ≤ 15 秒 | 接收至首次有效分派；模型异常单独统计 |
| 后续事件直通 | p95 ≤ 1 秒 | 事件持久化至目标执行邮箱可读 |
| 并发隔离 | 4 个任务并行时可继续接收新请求 | 一个任务执行 5 分钟，其他任务仍可接收与调度 |
| 路由质量 | 评估集准确率 ≥ 95%，所有标注歧义样本进入澄清 | 至少 100 条人工标注事件，单独统计误关联 |
| 事件可靠性 | 200 条带重试和乱序的回放无已确认事件丢失 | 对账源事件、入库事件和终态处理记录 |
| 写入安全 | 受测旧版本、撤权和重复事件不产生新增越权写入 | 故障注入与外部动作账本核验 |
| 故障恢复 | 重启后 2 分钟内恢复可调度任务或展示明确等待原因 | 杀进程、断开设备、模拟结果回执丢失 |
| 成本控制 | 每任务、每天、主动工作分别设限 | 使用协议可提供的实际用量和计价信息；缺失用量或报价时显示估算及待对账 |
| 通知质量 | 同一状态不因重放而重复发送；无普通工具刷屏 | 通知账本和测试接收箱对账；外部未知结果转人工核对 |

取消请求应在持久接收后 2 秒内关闭后续动作授权；已运行命令的实际终止时间单独测量。在线且可终止的测试命令目标为 10 秒内确认停止，离线和不可中断场景必须显示真实状态。

价值评估采用两周试点：先记录人工处理 20 个代表性任务的上下文补充次数、主动追问次数、验收耗时，再对相似任务使用系统。目标是单任务人工上下文补充次数中位数下降 30%，同时验收通过率不下降。该目标是试点假设，不能用模拟耗时工具证明真实研发质量。

| 问题 | 当前采用的默认决策 | 需要验证的内容 |

## 14 v0.2 实施与验收口径

本设计与《实施基线》《接口契约》共同使用，六周表示工作量规划，实施可按依赖并行推进。服务端采用 Python 3.12、FastAPI、SQLAlchemy，开发用 SQLite 单进程，部署用 PostgreSQL；工作台采用 Node 22、React/TypeScript/Vite。全部业务 API 使用 `/api/v1`。Codex app-server 负责代码任务执行，控制服务负责来源身份、项目绑定、版本控制、审批和外部动作账本。

Codex 持续会话与任务持久化需要配合外部请求 ID、thread/turn ID、审批请求和实际产物对账。暂停先撤销后续动作许可，再请求中断并等待结果确认。连接中断时保留未知状态并核对实际文件和外部动作。独立 Git 工作区的安全边界由操作系统权限、Codex 策略、可用隔离机制及凭据隔离共同落实。

所有指标与 AC 清单均为待验证目标。离线假 Codex 和假外部服务用于协议与故障测试；真实 Codex、钉钉、Redmine、PostgreSQL 并发及人工验收逐项记录状态。真实账号监听和对外发送由用户配置与授权决定。当前开发遵守工作区约定，真实钉钉、Redmine、Git 远端发送及部署须留待接入验收。
