## 工作流原理

它是“业务目标 → 设计决策 → 工程实现 → 浏览器证据 → 审查修正 → 项目记忆”的反馈闭环。

| 环节 | 本项目如何使用 | 解决的问题 |
| --- | --- | --- |
| 业务理解 | 先读现有组件、主要操作、实施基线与接口契约 | 避免为美观改变业务 |
| 设计决策 | Frontend Design 提供信息层级、排版和视觉方向方法；新模块研究真实参考 | 避免直接堆组件与随机风格 |
| 项目记忆 | DESIGN.md 记录当前身份与已确认规则，AGENTS.md 要求后续任务先读 | 避免每次新增页面重新选风格 |
| 工程依据 | Modern Web Guidance 检索具体 Web 能力 | 避免过时实现和不必要的兼容性问题 |
| 实际反馈 | Playwright 打开当前 React 页面、操作真实 DOM、截图与记录 trace | 发现代码阅读和构建无法揭示的页面问题 |
| 视觉审查 | 打开截图，结合 Impeccable 的层级、一致性和认知负担标准审查 | 区分“程序运行”与“设计合格” |
| 迭代复验 | 修复授权范围问题，重新操作、截图并检查 | 以证据证明修正有效 |

用户以后主要描述“谁使用、完成什么任务、希望什么感受”，通常无需决定每个字号和间距。Agent 依项目规则自行决策；业务歧义或超出授权范围的重大变更仍需明确。

技能不提供自动审美保证。本轮截图流程曾发现：设置页还在“正在检查”时就被截图。修正的是测试等待条件，随后复验显示加载完成的真实状态。另一次检查捕捉到并行修改中的白屏，说明断言和截图能够拒绝错误结果，而非一律报告成功。

## 视觉审查结果

审查方式为实际打开各轮代表性截图，覆盖桌面事件详情、空搜索、管理设置、Worker 列表、平板页面及窄屏事件/抽屉；不是声称逐张人工审完全部输出。

已确认：

- 当前主题、选中状态、中文折行和主要信息层级在样本中正常显示。
- 三种视口的已截页面无整页横向溢出，页面 JavaScript/API 错误会令测试失败。
- 项目抽屉按原生 modal 打开；抽检 Tab 焦点保留在弹窗内，Esc 后回到添加项目按钮。
- 第二轮起设置页等待加载完成；抽屉截图不再把模态框下方背景当成主体。

保留的改进项：

1. **P2：窄屏导航过高。** 390×844 下导航与账号区域占据约半屏以上，用户需滚动才能充分查看事件；适合后续明确的移动端导航优化任务，本次未重设计。
2. **P2：局部旧配色仍存在。** 当前紫色主操作旁仍有青绿色标签、说明与展开项，设计身份存在局部残留；DESIGN.md 已明确区分全局 Token 与遗留局部规则。

只读 Impeccable 检测对指定的 `main.tsx`、`style.css`、`workbench-theme.css` 返回 8 条 warning（6 条侧边强调、1 条圆角边框强调、1 条字体提示），进程退出码 2；不能写成“无问题通过”。字体提示命中被覆盖的历史 Inter 声明，实际计算字体为 Segoe UI / Microsoft YaHei。状态选中条和旧样式需结合实际用途判断，不据机械审美规则批量删除。
