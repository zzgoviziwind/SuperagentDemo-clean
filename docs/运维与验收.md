# SuperAgent 运维与验收

## 交付状态

以 `docs/实施基线.md` 为范围，以 `docs/handoffs/qa.md` 为最新实测记录。离线黑盒使用真实 HTTP 服务、临时 Git 仓库和独立假 Codex 进程。真实 Codex 修复、钉钉账号、Redmine 测试项目、PostgreSQL 并发与 Docker 运行需分别验收。

## 账号和配置

运行环境为 Python 3.12、Node 22、Git。依赖安装在本项目 `.venv` 和 `apps/web/node_modules`。Python 安装使用 `requirements-lock.txt`，前端存在锁文件时使用 `npm ci`。

从 `deploy/environment.example` 查看配置名。Windows 从本机凭据管理或受控启动会话注入环境变量。Compose 复制到 `deploy/.env` 后填写，限制文件读取权限。令牌、模型账号、Redmine API key、钉钉账号材料均由本机凭据管理持有，产品设置只保存环境变量名称等引用。

| 配置 | 用途 |
| --- | --- |
| `SUPERAGENT_DATABASE_URL` | SQLite 单进程开发或 PostgreSQL 连接 URL |
| `SUPERAGENT_API_TOKEN` | API Bearer 令牌，外部访问必填 |
| `SUPERAGENT_WORKSPACES_ROOT` | 与源仓库分离的任务工作区根目录 |
| `SUPERAGENT_CODEX_EXECUTABLE` | 本机 Codex 绝对路径，或 JSON argv 数组 |
| `POSTGRES_PASSWORD` | Compose 数据库口令，使用 URL 安全字符或正确编码 |
| `SUPERAGENT_REPOSITORIES_PATH` | Compose 只读源仓库目录，容器内项目路径为 `/repos/<仓库>` |

首次启动保持真实连接关闭。管理员绑定项目目录、基线分支、固定测试命令、来源群或 Redmine project ID，以及可验证的外部身份映射。模型正文中的身份和授权不能作为账号映射。Codex 使用本机已配置账号，首次真实测试只选择专用小仓库。Docker 镜像当前包含控制面和 Git，Codex 执行器需单独配置并验证。

调度默认关闭。通过管理员设置入口明确启用 `scheduler_enabled`，配置 `max_concurrent_tasks`（首版最多 4）、`budget_hard_limit_micros` 和正数 `budget_reservation_estimate_micros`。预算单位为配置币种的百万分之一，预留金额应按模型价格与单次上限估算。模型用量未知时预留会保持待对账，额度不足时先核对已有预留。

连接器通过管理员 `PATCH /api/v1/settings` 配置，字段 `connectors.redmine` 包含 `enabled/base_url/project_ids/user_id/api_key_env/poll_seconds`。`api_key_env` 填本机保存 API key 的环境变量名，默认 `HLZJ_REDMINE_API_KEY`。`connectors.dingtalk` 包含 `enabled/executable/profile/self_ids/kind/chat_id`，使用本机已登录 DWS 的 profile，凭据由其本机管理。开发阶段保持 enabled 为 false。外部身份通过 `/api/v1/identities` 绑定 `source/actor_id/user_id/project_ids/permissions`，request 权限需要显式授予目标项目。

## Windows 启动和停机

在项目根目录运行以下命令。

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
# 先由凭据管理向当前会话注入 SUPERAGENT_API_TOKEN 等环境配置
.\deploy\start.ps1
```

`start.ps1` 以隐藏窗口启动 API，默认监听 `127.0.0.1:8765`，健康成功后返回。日志在 `deploy/state/stdout.log`、`stderr.log`。进程身份记录在 `deploy/state/service.json`。配置 Codex 时工作区目录必须存在且可写，源仓库必须干净。

安装 Node22 依赖后先构建工作台，再运行上面的启动脚本，可直接访问 `http://127.0.0.1:8765`。

```powershell
Push-Location apps/web
npm ci
npm run build
Pop-Location
```

前端开发入口在 `apps/web`，运行 `npm run dev` 后访问终端给出的本机地址，并把实际开发地址加入后端 `SUPERAGENT_ALLOWED_ORIGINS`。Vite 转发原始认证和会话 Cookie，用户通过登录页建立自己的会话。

总控当前交付实例使用 `data/workbench.db` 和 `data/workspaces`，由其原启动方式管理。`deploy/start.ps1` 新建实例的默认数据位于 `deploy/state`，两者配置分别核对。脚本测试使用 `-StateDirectory` 指定独立目录和单独端口，避免共用服务记录。

```powershell
$Headers = @{ Authorization = "Bearer $env:SUPERAGENT_API_TOKEN" }
Invoke-RestMethod http://127.0.0.1:8765/health -Headers $Headers
.\deploy\stop.ps1
```

先暂停任务并核对执行结果，再停机。停机脚本终止所拥有的进程树，并校验 PID 启动时间。强制停机会留下结果未知的执行，重启后先对账。脚本只管理自身启动的服务。其他方式启动的服务由对应进程管理器停止。

## Compose

```powershell
Copy-Item deploy/environment.example deploy/.env
# 在本机填写两个口令和源仓库路径
docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.yaml up --build -d
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
```

Web 默认 `http://127.0.0.1:8080`，API 默认 `http://127.0.0.1:8765`。PostgreSQL 只在 Compose 内网监听，数据库和任务目录分别位于持久卷。容器 API 强制配置访问身份。Nginx 转发原有 Authorization 和 Cookie，用户通过登录页获得 HttpOnly 会话。多用户身份通过 `SUPERAGENT_USERS_JSON` 环境配置，采用 admin/member/viewer 角色，管理员令牌由 `SUPERAGENT_API_TOKEN` 提供。

默认 Origin 允许本机 8080，修改域名或端口时同步调整 `nginx.conf` 和允许 Origin 配置。容器代理登录要求可信 TLS 前置代理设置并清理 `X-Forwarded-Proto`，Nginx 继续传给 API。镜像 API 信任专用 Compose 网络中的代理头，API 发布端口维持 localhost，并限制网络成员。公网接入通过 TLS 入口提供用户登录，核验 Web/API 鉴权、角色、下载和事件注入。Docker 环境的完整 HTTPS 登录需实际部署后验收。

正常停机使用 `docker compose --env-file deploy/.env -f deploy/compose.yaml stop`。升级先停止调度、核对在途任务、备份，再构建替换。数据库当前的版本迁移能力以控制层交付记录为准，回退前检查兼容性。卷的删除与重建需要独立确认数据保存情况。

## 备份和恢复

备份要求控制服务、执行器、连接器及其他写入进程均已停止，以保持数据库、文件和审批的同一停机切面。数据库与目录应纳入同一备份。工作区 clone 的 Git 元信息、产物文件和数据库均需保留。备份目录必须在数据目录之外。

```powershell
.\deploy\stop.ps1
# SUPERAGENT_DATABASE_URL 应与实际服务配置一致
.\deploy\backup.ps1 -DataRoot .\deploy\state -Destination .\deploy\backups\snapshot-001
.\deploy\restore.ps1 -Snapshot .\deploy\backups\snapshot-001 -Destination .\deploy\restored\recovery-001
```

`snapshot.py` 使用 SQLite backup API 或 PostgreSQL `pg_dump`，记录 SHA-256 清单。PostgreSQL 需要已安装与服务端兼容的 `pg_dump`，连接口令经进程环境提供。备份数据目录包含工作区和文件产物，数据库内容产物由数据库备份保存。恢复前检查 hash，不完整备份拒绝恢复，已有目标目录拒绝覆盖，符号链接和 Windows junction 拒绝打包。

恢复目录生成 `data/`、数据库快照及 `RECONCILIATION_REQUIRED.txt`。SQLite 将 `SUPERAGENT_DATABASE_URL` 指向恢复的 `database.sqlite`。PostgreSQL 由管理员创建全新空库，设置 `PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE` 后运行 `pg_restore --single-transaction --no-owner --no-privileges --dbname <新库名> <恢复目录/database.dump>`，再配置连接 URL。运行这一步会写入指定新库，应单独核对目标。

恢复后先保持 Codex 执行器和全部外部连接关闭。核对任务 revision、审批状态、产物清单，以及已发送动作的外部对象 ID。未知发送结果需查询目标渠道，无法确认的继续保留 unknown，确认未发送后再决定是否重试。禁止直接重放整个动作队列。工作区路径引用应保持原挂载路径，迁移路径需要逐项校验已有任务引用后才能继续。确认账本与外部结果一致后，再逐个恢复执行器和连接器。

任务的 `outcome_unknown` 为 true 时，普通暂停、恢复、取消和重试均被阻断。管理员确认原进程已停止后，通过 `POST /api/v1/tasks/{id}/reconcile` 提交 `outcome: stopped`、核验 evidence 和当前 expected_state_version，任务进入 paused 后再显式恢复。确认放弃时使用 abandoned，保留原证据并结束任务。外部交付 unknown 则用独立的 delivery reconcile 入口记录外部核验结果，两者分别核对。

日常目标为每日一致性备份，RPO 24 小时、RTO 4 小时。已完成离线 SQLite 演练及假 Redmine 模拟写入回执丢失后的数据库恢复，重复 publish 返回原 unknown，远端计数保持 1。PostgreSQL 和全量任务恢复耗时需现场记录，目标尚待实测。

## 数据保留

默认规划为日志和原始事件 30 天，任务产物、审批及审计 90 天。当前无自动清理作业，管理员根据空间和引用关系安排清理，清理前核对任务引用与备份。备份由管理员按同一保留计划归档淘汰。源仓库和未验收任务工作区需要单独核对后处理。

## 验收和故障诊断

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests/e2e -v
```

| 场景 | 必须观察的证据 |
| --- | --- |
| 任务接收到交付 | 项目绑定、独立目录、真实子进程审批、可下载产物、工具事件中的实际测试证据、人工验收 |
| 取消和迟到 | 假进程中断后延迟完成事件不能覆盖 cancelled |
| 改方向 | revision 增加，旧动作 hash 的批准返回 409 |
| 重复事件 | 十次重投、重启后再投，保持唯一事件且未映射身份不能建执行任务 |
| 恢复 | completed 持久化，unknown 动作保留，篡改文件校验失败，已有恢复目录不被覆盖 |

启动失败查看 stderr，核对 Python、依赖、目录权限、数据库连接、端口和令牌。任务排队检查调度器配置和执行器可用性。审批等待检查动作内容及当前 revision。停止未知时先核对进程树与任务记录。数据库连接正常与 `/health` 成功需要结合任务黑盒验收，分别记录证据。

真实渠道验收使用独立钉钉授权测试会话、Redmine 测试项目及专用小仓库，记录账号映射、请求 ID、任务 ID、动作 hash、外部对象 ID 和人工验收人。总控负责批准并组织这些接入，离线脚本不触发真实发送。

最终离线命令已通过 18 项，用时 202.108 秒，覆盖最新治理、审批、人工对账、采集器验证和备份恢复。Windows 脚本独立状态目录启停通过，进程树关闭采用 .NET 主路径及 taskkill 兼容后备。Docker、PostgreSQL、真实 Codex 修复、真实钉钉/Redmine 和浏览器视觉验收分别保留待验收状态。
